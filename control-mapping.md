# Sigil Open Framework Control Mapping

Prepared: 2026-04-26

## Introduction to Sigil Open Framework

The Sigil Open Framework (SOF) is a deterministic governance layer for autonomous AI agents performing high-stakes actions. SOF does not try to make a model generally safe, fair, private, or explainable. Its purpose is narrower and more auditable: bind policy-bound human intent to machine execution before an agent reaches tools, credentials, wallets, APIs, filesystems, cloud infrastructure, or other external systems.

SOF does this through a small set of repeatable primitives:

- A human or accountable operator defines execution policy in a signed Sigil Warrant, usually expressed as `warranty.md`.
- The agent or integration layer declares the action it is about to take as an intent.
- Sigil Sign or an Open Execution Engine (OEE) policy evaluator checks the declared intent against the signed policy before execution.
- Approved actions receive a short-lived Intent Attestation that binds the action, policy hash, agent identity, framework, time, and verification claims.
- Denied actions do not receive execution proof.
- Threshold actions can enter a human hold workflow instead of being silently approved.
- Gateways, hooks, or credential brokers reject execution or credential release when valid proof is absent, expired, replayed, or mismatched.
- Sigil Command, gateway logs, and Sigil Vault audit records provide the sampleable evidence trail.

This mapping treats SOF as a control family for pre-execution enforcement. It should be used as evidence for agentic execution governance, not as a substitute for an AI management system, model evaluation program, legal review, privacy impact assessment, fairness program, supplier due diligence process, or incident response function.

## Document Guide

This document is written for auditors, GRC leads, procurement risk teams, and customer security reviewers. Each row is intended to stand alone so it can be copied into a statement of applicability, audit program, control narrative, or risk register.

Column conventions:

- `Control ID` identifies the source control, subcategory, or profile row.
- `Control surface` paraphrases the control so a reviewer does not need to switch documents before understanding the mapping.
- `Mapping strength` uses three values:
  - `Primary`: SOF can serve as primary evidence for the governed execution portion of the control.
  - `Partial`: SOF supplies material, sampleable evidence, but the organization must operate a separate process or control owner for the rest.
  - `Out of scope`: SOF should not be claimed as satisfying the control. At most, SOF records may inform a separate control.
- `SOF primitive` names the component or artifact carrying the control load.
- `Evidentiary satisfaction` states what an auditor can sample or verify.
- `What remains the organization's responsibility` is populated for `Partial` rows. For `Primary` and `Out of scope` rows, it is marked `N/A`.

The phrase `Primary` does not mean SOF certifies the organization against the whole framework. It means SOF is primary evidence for the scoped execution-governance claim: whether a high-stakes agent action was authorized before execution.

For controls marked `Primary` or `Partial`, a reusable audit package should include:

- Signed Sigil Warrant and public verification key.
- Policy version history, approval record, and resulting `policyHash`.
- Sample approved Intent Attestations with action class, agent ID, framework, issue time, expiry, and policy hash.
- Sample denied intents showing matched policy rule and no issued attestation.
- Sample pending intents showing hold creation, resolver identity, decision, expiry behavior, and post-resolution outcome.
- Gateway tests showing write operations without valid proof fail.

## Common Audit Objections

**Does SOF satisfy ISO/IEC 42001, NIST AI RMF, or Berkeley by itself?**

No. SOF supplies primary evidence for the pre-execution enforcement portion of selected controls. It does not replace an AI management system, risk assessment, impact assessment, model evaluation program, supplier due diligence process, privacy program, or incident response program.

**Is this just logging?**

No. Logging records what happened. SOF records and enforces the decision before execution. A denied or held action becomes evidence even when the external transaction, tool call, credential release, or infrastructure mutation never happens.

**Does SOF prove the model is safe?**

No. SOF makes a specific class of unsafe or unauthorized action paths harder to exercise. It does not prove the model is valid, reliable, fair, interpretable, private, or aligned in the general sense.

**Can the agent modify its own policy?**

That should be treated as a high-risk design and is not part of this mapping claim. The mapped control claim assumes the Sigil Warrant is human-controlled, signed by an accountable operator, and verified before use. An AI-interpretable policy is compatible with SOF; an AI-writable policy requires separate governance and independent human oversight.

**What about fail-open behavior?**

High-stakes deployments should configure fail-closed behavior at the hook and gateway layers. Vault should hard-reject missing, invalid, expired, replayed, or mismatched attestations. If an integration is configured to fail open for lower-risk workflows, that should be documented as a residual risk and should not be used as primary evidence for high-stakes enforcement controls.

**How should procurement use this artifact?**

Procurement and risk teams should treat SOF as a control layer for autonomous execution risk. In a vendor review, ask which agent actions are governed, which policy signed them, which proof must be presented before execution, how denials and holds are recorded, and which actions remain outside SOF.
